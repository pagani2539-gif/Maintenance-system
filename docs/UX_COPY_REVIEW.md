# รายงานตรวจทาน UX Copy (ข้อความในระบบ) ก่อนขึ้น Production

> จัดทำ: 2026-07-05 · ขอบเขต: ข้อความที่ผู้ใช้เห็นทั้งหมด (frontend `client/src` + backend message ที่ surface ขึ้น UI)
> สถานะ: **เอกสารรีวิว — ยังไม่แก้โค้ด** รออนุมัติรายการก่อนลงมือ
> เกณฑ์: Clear · Concise · Consistent · Useful · Human (จาก ux-copy principles)

## สรุปผู้บริหาร
Copy ของระบบ**อยู่ในเกณฑ์ดีถึงดีมาก** — โครงสร้าง confirm dialog, success message, และ error message ส่วนใหญ่เขียนถูกหลัก มีการเตือน "ย้อนกลับไม่ได้" ในจุดสำคัญ และไม่มีการแสดงราคา/เงินในหน้าจอหลักแล้ว

พบประเด็นควรแก้ **แบ่งเป็น 3 ระดับ**:
- 🔴 **ควรแก้ก่อนขึ้น (P1)**: 3 กลุ่ม — ความไม่สม่ำเสมอของคำเรียก "สถานี", error message กว้างเกินไปในหลายจุด, empty state ไม่แยกกรณี "ยังไม่มีข้อมูล" กับ "ค้นหาไม่เจอ"
- 🟡 **ควรแก้ถ้ามีเวลา (P2)**: อีโมจิ 🎉 ในบาง success, คำพ้อง "อุปกรณ์/พัสดุ", confirm dialog บางใบขาดคำเตือนย้อนกลับไม่ได้
- 🟢 **ผ่าน / เก็บไว้อ้างอิง (P3)**: ส่วนใหญ่ของระบบ

## หมวด 1 — Terminology & Consistency 🔴 P1 (สำคัญที่สุด)

### 1.1 คำเรียก "สถานี" ไม่สม่ำเสมอ — พบ 4 คำใช้ปนกัน
ในหน้า/ฟีเจอร์เดียวกันใช้คำต่างกัน ทำให้ผู้ใช้สับสนว่าเป็นสิ่งเดียวกันหรือไม่:

| ตำแหน่ง | คำที่ใช้ตอนนี้ | ไฟล์ |
|---|---|---|
| หัวข้อหน้า | "บริหารจัดการสถานีและจุด**ตรวจ**" | `StationSearch.tsx` |
| ปุ่มเพิ่ม | "เพิ่ม**หน่วยงาน**ใหม่" | `StationSearch.tsx` |
| หัวข้อ modal | "เพิ่ม**สถานี**ใหม่" | `StationSearch.tsx` |
| filter label | "ประเภท**หน่วยงาน**" | `StationSearch.tsx` |
| placeholder ค้นหา | "พิมพ์ค้นหา**ด่าน**/สถานี..." | `NewWithdrawal.tsx:` |
| StationSelector | "ไม่พบ**สถานี**? คลิกเพื่อเพิ่ม" | `StationSelector.tsx:617` |

**แนะนำ**: เลือกคำหลัก **"สถานี"** เป็นมาตรฐาน (สอดคล้องกับ code `stations`, `STN-` prefix, และ modal ที่ใช้อยู่) แล้วแก้ทุกจุดให้ตรง — ปุ่ม "เพิ่มหน่วยงานใหม่" → "เพิ่มสถานีใหม่", "ประเภทหน่วยงาน" → "ประเภทสถานี", หัวข้อหน้า → "บริหารจัดการสถานี" (คำว่า "ด่าน" เก็บไว้ได้เฉพาะ placeholder ตัวอย่างเพราะเป็นภาษาพูดที่ผู้ใช้คุ้น แต่ label/หัวข้อควรเป็น "สถานี" ล้วน)

### 1.2 "อุปกรณ์" vs "พัสดุ" — พบปนกัน 🟡 P2
- ฝั่งงานเบิก/คลังใช้ "อุปกรณ์" เป็นหลัก (เพิ่มอุปกรณ์, เบิกอุปกรณ์)
- ฝั่ง PO ใช้ "พัสดุ" (เพิ่มพัสดุใหม่, สแกนพัสดุสต็อกต่ำ, ตรวจรับพัสดุ) — `NewPurchaseOrderModal.tsx`, `purchaseOrders.js`
- Sidebar/เมนูใช้ "พัสดุ" (สมุดบัญชีสต็อก, การจัดซื้อพัสดุ)

**แนะนำ**: ยอมรับได้ว่า PO/จัดซื้อใช้ "พัสดุ" (เป็นศัพท์ราชการที่เหมาะกับบริบทจัดซื้อ) แต่ควร**ตัดสินใจอย่างตั้งใจ**และจดไว้ใน glossary ว่า: คลัง+เบิก = "อุปกรณ์", จัดซื้อ+บัญชี = "พัสดุ" — ถ้าจะให้เป๊ะสุดควรเลือกคำเดียวทั้งระบบ (แนะนำ "อุปกรณ์") แต่ priority ต่ำกว่า 1.1

### 1.3 สถานะ vs ประเภท — ✅ ผ่าน
ตรวจแล้วใช้ถูกต้องตามหลัก ([[terminology-status-vs-type]]): "ประเภทการเบิก/ประเภทสถานี" (immutable) แยกจาก "สถานะงาน/สถานะ S/N" (mutable) ชัดเจน ไม่พบการสลับ

## หมวด 2 — Error Messages 🔴 P1

### 2.1 Error กว้างเกินไป — ไม่บอกวิธีแก้
พบข้อความ `'เกิดข้อผิดพลาดในการบันทึกข้อมูล'` / `'เกิดข้อผิดพลาดในการอัปเดตสถานะ'` ซ้ำในหลายไฟล์ (`NewRepair.tsx:157`, `NewClaim.tsx:157`, `RepairDetail.tsx:184/244`, `ClaimList.tsx:143/159`) — เป็น fallback ที่ผู้ใช้ทำอะไรต่อไม่ถูก

**แนะนำ**: จุดที่ backend ส่ง message เฉพาะเจาะจงกลับมาแล้ว ให้ frontend แสดง `err.response?.data?.message` เป็นหลัก (บางไฟล์ทำแล้วเช่น `InventoryList.tsx:224` — ควรทำให้ครบทุกไฟล์) และ fallback เปลี่ยนเป็น: **"บันทึกไม่สำเร็จ กรุณาลองใหม่อีกครั้ง หากยังพบปัญหาโปรดติดต่อผู้ดูแลระบบ"** (บอก next step)

### 2.2 ตรวจ field message/error ให้ตรง (จุดเสี่ยงจาก migration) 🔴 P1
Backend ส่งข้อความ error ปนกัน 2 field: `{ message: ... }` (inventory, withdrawals, PO) และ `{ error: ... }` (users, stations, contracts, repairs บางจุด — `repairs.js:587/650`). Frontend ต้องอ่าน field ให้ตรงกับ controller ที่เรียก ไม่งั้นผู้ใช้เห็น "undefined"

**แนะนำ**: (ก) ระยะสั้น — frontend ใช้ `err.response?.data?.message ?? err.response?.data?.error ?? '<fallback>'` ทุกจุดเพื่อกันพลาด; (ข) ระยะยาว — รวม field ให้เป็นมาตรฐานเดียว (แนะนำ `message`) ทั้ง backend เพื่อลดความสับสน — **ควรทำ (ก) ก่อนขึ้น production เป็นอย่างน้อย**

### 2.3 Error ที่เขียนดีแล้ว ✅
- "จำนวนที่เบิกเกินจำนวนอุปกรณ์คงเหลือในคลัง" (บอกสาเหตุชัด)
- "ไม่สามารถลบอุปกรณ์ได้ อาจมีการใช้งานอยู่ในประวัติการเบิก" (`InventoryList.tsx:344` — บอกสาเหตุ+นัยยะ)
- "ต้องมีผู้ดูแลระบบ (Full) อย่างน้อย 1 คน" (`users.js` — กันผู้ใช้ล็อกตัวเองออก)
- validation ความยาว ("ชื่อโครงการยาวเกินไป (ไม่เกิน 100 ตัวอักษร)") — บอก limit ชัดเจน ดีมาก

## หมวด 3 — Confirmation Dialogs 🟡 P2

### 3.1 Destructive action ที่ **มี** คำเตือนย้อนกลับไม่ได้แล้ว ✅
ลบสถานี (`StationSearch.tsx:436`), ลบ backup (`Settings.tsx:332`) — มี "ไม่สามารถย้อนกลับได้" ครบ

### 3.2 Destructive action ที่ **ขาด** คำเตือนย้อนกลับไม่ได้ 🟡
ควรเพิ่มประโยคเตือนผลถาวรให้ dialog เหล่านี้ (ปัจจุบันมีแค่ title/ถามสั้น):
- ลบใบสั่งซื้อ — `PurchaseOrderList.tsx:73`
- ลบรายการแจ้งซ่อม/เคลม — `RepairList.tsx:151`, `RepairDetail.tsx:257`
- ลบรายการธุรกรรม — `TransactionList.tsx:77`
- ลบอุปกรณ์ — `InventoryList.tsx:333`

**แนะนำ**: เติมบรรทัด "การดำเนินการนี้ไม่สามารถย้อนกลับได้" ใน `message` ให้ครบทุกใบ (ให้ token เดียวกันกับที่ใช้ในลบสถานี/backup เพื่อความสม่ำเสมอ)

### 3.3 ปุ่มใน dialog ✅
ส่วนใหญ่ปุ่มระบุ action ("ยืนยันการลบ...", "ยืนยันการตรวจรับ") ไม่ใช่ "OK/ยกเลิก" ลอยๆ — ดี; flow กู้คืน DB ให้พิมพ์ "RESTORE" ยืนยัน — ดีเยี่ยม เก็บไว้

## หมวด 4 — Empty States 🔴 P1

### 4.1 ไม่แยกกรณี "ยังไม่มีข้อมูลเลย" กับ "ค้นหา/กรองไม่เจอ"
หลายหน้าแสดง "ไม่พบข้อมูลที่ค้นหา" แม้ตอนที่ยังไม่มีข้อมูลในระบบเลย (เช่น หน้า Inventory/Station ตอนเริ่มใช้งานจริงครั้งแรก จะว่างเปล่า) ทำให้ผู้ใช้ใหม่ไม่รู้ว่าต้องเริ่มยังไง

**ตัวอย่างที่ทำถูกแล้ว** (ใช้อ้างอิง): `Settings.tsx:716-717` "ยังไม่มีโลโก้สำหรับบริษัทนี้ / คลิกปุ่ม 'อัปโหลดโลโก้' เพื่อเริ่มต้น" — มีทั้งบอกสถานะ + ชวนเริ่ม

**แนะนำ** — แยก 2 ข้อความต่อ list:
- ว่างเพราะยังไม่มีข้อมูล → ชวนสร้าง เช่น "ยังไม่มีอุปกรณ์ในคลัง — กด **เพิ่มอุปกรณ์ใหม่** เพื่อเริ่ม"
- ว่างเพราะ filter/search → "ไม่พบผลลัพธ์ที่ตรงกับคำค้นหรือตัวกรอง ลองปรับเงื่อนไขใหม่"

จุดที่ควรแก้: `InventoryList` (grid), `StationSearch:943`, `WithdrawalList`, `RepairList`, `ClaimList`, `PurchaseOrderList`, `AuditLogs:160`, `TransactionList`

### 4.2 Empty state ที่ดีอยู่แล้ว ✅
Dashboard widget ("ยังไม่มีกิจกรรมในช่วงเวลานี้", "ยังไม่มีข้อมูลผู้เบิก"), StationSelector ("ไม่พบสถานี? คลิกเพื่อเพิ่มสถานีใหม่" — บอก next step) — เขียนดี

## หมวด 7 — Success / Loading / Tone 🟡 P2

### 7.1 อีโมจิ 🎉 ใน success message — ใช้ไม่สม่ำเสมอ
บาง success มี 🎉 (`NewRepair.tsx:151` "🎉 ส่งข้อมูลแจ้งซ่อมเรียบร้อยแล้ว", `NewClaim`, `PendingReturns`, `PurchaseOrderList`, `NewPurchaseOrderModal`) บางอันไม่มี (`RepairDetail.tsx:239` "แก้ไขข้อมูลเรียบร้อยแล้ว", `StationSearch` "เพิ่มสถานีใหม่เรียบร้อยแล้ว")

**แนะนำ**: เลือกแนวทางเดียว — บริบทงานราชการ/องค์กร แนะนำ **ตัด 🎉 ออกทั้งหมด** ให้โทนสุภาพสม่ำเสมอ (success ที่ดีคือชัดเจน ไม่ต้องฉลองเว่อร์) หรือถ้าจะเก็บ ให้ใช้เฉพาะ action ใหญ่ (สร้างใบใหม่) เท่านั้นและใช้ให้ครบทุก action ประเภทเดียวกัน

### 7.2 Loading state ระหว่างงานนาน 🟡
Backup/restore/import ใช้เวลานาน ควรมีข้อความตั้งความคาดหวัง เช่น "กำลังสำรองข้อมูล อาจใช้เวลาสักครู่ กรุณาอย่าปิดหน้านี้" — ตรวจว่ามีครบ (ปัจจุบันมี loading state ปุ่มแต่ควรเช็คข้อความระหว่างรอ)

## หมวด 8 — No-Money-Display Compliance 🟢 P3 (ผ่าน + 1 จุดเฝ้าระวัง)
- ✅ Dashboard: ไม่มี copy เรื่องเงิน/ราคาที่แสดงผล (ตรวจแล้วไม่พบ "ราคา/บาท/มูลค่า/งบ")
- ✅ ฟอร์มเพิ่มอุปกรณ์: **ไม่มี** input/label "ราคาต่อหน่วย" ที่มองเห็นแล้ว (`unit_price` ถูกส่งเงียบๆ เป็น 0 — `InventoryList.tsx:185`); เหลือแค่ "ระยะเวลาประกัน (เดือน)" ซึ่งไม่ใช่เงิน = ผ่านนโยบาย
- 🟡 **จุดเฝ้าระวังเดียว**: `excelImporter.ts:29` ยังรับ alias คอลัมน์ "ราคาต่อหน่วย"/"ราคา" ตอน import (ไม่ใช่ display แต่ template ยังพูดถึงราคา) — ควรพิจารณาลบ alias นี้ + ลบคอลัมน์ราคาออกจากเทมเพลต Excel ให้สอดคล้องนโยบาย (priority ต่ำ เพราะไม่ใช่หน้าจอ)
- ℹ️ ใน `types.ts` ยังมี `total_cost`/`total_price`/`cost_exceeds_threshold` เป็น type — เป็นข้อมูลเบื้องหลัง ตรวจว่าไม่ถูก render (ยืนยันแล้วว่า Dashboard ไม่แสดง) = ปลอดภัย

## Glossary คำมาตรฐานที่แนะนำ (ใช้อ้างอิงงานในอนาคต)
| ความหมาย | ใช้คำนี้ | เลี่ยง |
|---|---|---|
| จุดตั้งอุปกรณ์/ด่าน | **สถานี** (label/หัวข้อ) | หน่วยงาน, จุดตรวจ (ด่าน = ใช้ได้เฉพาะ placeholder ตัวอย่าง) |
| ของในคลัง | **อุปกรณ์** (คลัง/เบิก) · **พัสดุ** (จัดซื้อ/PO เท่านั้น) | สินค้า |
| เอาของออกจากคลัง | **เบิก** / **เบิกจ่าย** | ถอน, นำออก |
| เอาของกลับคลัง | **คืน** / **ส่งคืน** | รับเข้า (สงวนไว้สำหรับ PO receive = "ตรวจรับ") |
| ลบถาวร | **ลบ** + เตือน "ไม่สามารถย้อนกลับได้" | นำออก, ยกเลิก (ยกเลิก = สงวนสำหรับ action ที่ย้อนได้) |
| สถานะที่เปลี่ยนได้ | **สถานะ** | ประเภท |
| หมวดที่คงที่ | **ประเภท** | สถานะ |
