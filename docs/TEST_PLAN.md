## B. Authentication & สิทธิ์ผู้ใช้ (ทดสอบมือ)

### B1. Login / Logout
- [ ] Login ด้วย username/password ถูกต้อง → เข้า Dashboard ได้
- [ ] Login ผิดรหัส → ข้อความ error ภาษาไทยชัดเจน (ไม่ใช่ undefined / error ดิบ)
- [ ] ยิง login ผิดซ้ำๆ ติดกัน → โดน rate limit (เกณฑ์: 10 ครั้ง/15 นาที ต่อ IP → HTTP 429) และปลดล็อกเองเมื่อพ้นช่วงเวลา
- [ ] Logout แล้วกด Back → ไม่เห็นข้อมูล, ถูกเด้งกลับหน้า Login

### B2. วงจรรหัสผ่าน
- [ ] บัญชีใหม่ login ครั้งแรก → ถูก**บังคับ**เปลี่ยนรหัสผ่านก่อนใช้งาน (ข้ามไม่ได้)
- [ ] เปลี่ยนรหัสผ่านสำเร็จ → token/tab เก่าที่เปิดค้างไว้ใช้ต่อไม่ได้ (โดน 401 ให้ login ใหม่)
- [ ] Admin ปิดบัญชี (inactive) → user นั้น request ถัดไปโดน 401 ทันที (ไม่ต้องรอ token หมดอายุ)

### B3. Permission matrix
เตรียม user ทดสอบ 2 คน: `admin` (is_full) และ `user-limited` (เปิดสิทธิ์แค่ดู + สร้าง repair)
- [ ] `user-limited` ไม่เห็นเมนู/ปุ่ม: จัดการผู้ใช้, Audit Logs, Settings, ปุ่มลบใน repair/claim/PO/station
- [ ] ยิง API ตรง (เช่นด้วย curl/Postman) ด้วย token ของ `user-limited` ไปยัง endpoint ที่ไม่มีสิทธิ์ → ได้ 403 (`DELETE /api/repairs/:id`, `GET /api/users/audit-logs`, `POST /api/settings/...`)
- [ ] ยิง API โดย**ไม่มี** token → 401 ทุก route ยกเว้น `/api/auth/*` และ `GET /api`
- [ ] Admin แก้ permission ของ `user-limited` ขณะที่เขา login อยู่ → มีผลทันทีใน request ถัดไป (ระบบ re-fetch user ทุก request)

## C. วงจรงานซ่อม (Repairs) และงานเคลม (Claims)

### C1. สร้าง–แก้–ปิดงานซ่อม
- [ ] สร้างใบแจ้งซ่อม: เลือกสถานี + พิมพ์จุดติดตั้ง free-text + โครงการ/งาน + แนบรูป ≥ 2 รูป → บันทึกสำเร็จ
- [ ] เลขที่เอกสารรันรูปแบบ `RP-YYMMDD-NNN` และไม่ซ้ำเมื่อสร้าง 2 ใบติดกัน
- [ ] รูปที่อัปโหลดถูกบีบอัดฝั่ง client (ไฟล์ต้นทาง ~3-5MB → บนเซิร์ฟเวอร์เหลือหลัก ร้อยKB) และแสดงผลชัดเจน
- [ ] เปลี่ยนสถานะครบวงจร: รอดำเนินการ → กำลังซ่อม → เสร็จสิ้น + มอบหมายช่าง → ประวัติสถานะบันทึกครบทุก step พร้อมเวลา
- [ ] แก้ไขรายละเอียดใบซ่อม (สถานที่, อาการ, รูปเพิ่ม) → บันทึกและแสดงถูกต้อง
- [ ] ลบใบซ่อม (โดย user ที่มีสิทธิ์ `delete.repairs` เท่านั้น) → หายจาก list และ dashboard
- [ ] **เปลี่ยนอุปกรณ์ (replace device)** ในใบซ่อม: ระบุ S/N เก่า → S/N ใหม่ → บันทึกลงประวัติ `device_changes` และแสดงในหน้า detail ถูกต้อง

### C2. งานเคลม
- [ ] สร้างใบเคลม → เลขเอกสาร `CL-YYMMDD-NNN`
- [ ] บันทึก S/N อะไหล่ที่เปลี่ยน (ผ่าน SN scanner/กรอกมือ) → แสดงในหน้า detail และใบพิมพ์
- [ ] ลบ claim ต้องใช้สิทธิ์ `delete.claims` (user ที่มีแค่ `delete.repairs` ก็ลบ claim ได้ตาม gate ปัจจุบัน — ยืนยันพฤติกรรมนี้ตรงตามที่ต้องการ)

### C3. การพิมพ์ PDF
- [ ] ใบซ่อม/ใบเคลม พิมพ์ออกมาอยู่ใน **1 หน้า A4** ไม่ตกขอบ ไม่มีหน้าเปล่าท้าย
- [ ] Print dialog เลือกบริษัท → หัวกระดาษแสดงชื่อ/ที่อยู่/โลโก้บริษัทที่เลือก; เลือก "ไม่ระบุบริษัท" → หัวกระดาษ generic
- [ ] **ไม่มีราคา/จำนวนเงินปรากฏที่ใดในใบพิมพ์** (นโยบาย no-money-display)
- [ ] รูปแนบแสดงใน gallery 4 ช่อง (มีรูปจริง + placeholder ช่องว่าง)

### C4. ค้นหา/กรอง
- [ ] ค้นหาด้วยเลขเอกสาร, ชื่ออุปกรณ์, **สถานที่ (location)** → เจอถูกต้อง
- [ ] กรองช่วงวันที่ custom (start–end) → ผลตรงช่วง ไม่เพี้ยนวันจาก timezone
- [ ] Ctrl+K command palette ค้นข้าม repairs/claims/inventory/stations ได้

### C5. LINE Notify
- [ ] ตั้งค่า LINE Messaging API ในหน้า Settings แล้วเปลี่ยนสถานะใบซ่อม → ข้อความเข้า LINE ถูกต้อง (เลขเอกสาร, สถานะใหม่)
- [ ] กรณี**ไม่ได้**ตั้งค่า LINE → เปลี่ยนสถานะได้ปกติ ไม่ error ไม่ค้าง (แค่ log ว่า skip)
- [ ] กรณี LINE ตอบช้า/ล่ม → ระบบไม่ค้าง (มี timeout 10 วิ) และงานหลักสำเร็จ

## H. Regression เฉพาะจุดที่เคยพังตอน migration ⚠️ (สำคัญที่สุด)

- [x] **H1. Timezone**: **ผ่าน** — ทดสอบแล้ว 2026-07-04: `SELECT current_setting('TimeZone')` ผ่าน pool = `UTC` ถูกต้อง; สร้างใบเบิกใหม่จริงแล้วเปิดดูในหน้า WithdrawalList → แสดง "5 ก.ค. 2569 เวลา 01:14 น." ตรงกับเวลาไทยจริง (DB `now()` = 18:16 UTC = 01:16 ICT ใกล้เคียงตามลำดับเวลาที่สร้างจริง) ไม่มีการเพี้ยน ±7 ชม.
- [ ] **H2. ข้อมูลเก่าหลัง migrate**: สุ่มเทียบเวลา record เก่า 5 รายการระหว่าง SQLite เดิมกับ Postgres → ตรงกัน (เครื่อง production ต้องรัน `verify-migration.js` ผ่านทุกข้อ)
- [ ] **H3. JWT iat race**: สร้าง user ใหม่แล้ว login ทันทีภายในวินาทีเดียวกัน → ไม่โดน "Token หมดอายุเนื่องจากมีการเปลี่ยนรหัสผ่าน"
- [x] **H4. Error message field (เคสเบิกเกิน stock)**: **ผ่าน** — ทดสอบเบิกสายแลน 999 เส้น (คงเหลือ 40) แล้วได้ toast ข้อความไทยชัดเจน "จำนวนที่เบิกเกินจำนวนอุปกรณ์คงเหลือในคลัง" (ตรวจจับฝั่ง client ก่อนยิง API ด้วยซ้ำ) — ยังไม่ได้ทดสอบเคส inventory ชื่อซ้ำรอบนี้
- [ ] **H5. Concurrent writes**: เปิด 2 browser (2 user) เบิก item เดียวกันพร้อมกันหลายรอบ → stock ไม่ติดลบ, ไม่ deadlock, auto-PO ไม่สร้างซ้ำ 2 ใบ — จุดนี้คือเหตุผลหลักที่ย้ายมา Postgres ต้องพิสูจน์ว่าได้ประโยชน์จริง
